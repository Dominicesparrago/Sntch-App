01

What is SNTCH?

A classroom server in the room, with teacher and student apps on the local network.

One local classroom network

The ESP32-WROOM-32D creates its own Wi-Fi access point. The Android apps use the controller’s HTTP API for teacher and student tasks. Supported classroom state is saved on the controller’s LittleFS partition.

Normal classroom use does not require internet, a cloud service, an external router, a PC server, or a Raspberry Pi. The Arduino Uno is not required for core SNTCH operation.

02

Hardware and connections

The classroom system needs the controller and Android devices. The display and buttons are optional peripherals.

Core hardware

  • ESP32-WROOM-32D module on a compatible development carrier with USB/UART.
  • A suitable USB cable and stable USB power from a computer or power adapter.
  • Teacher Android phone/tablet and student Android device(s).

The exact carrier-board model is not identified. Confirm the board marking, USB connector, and header labels before wiring or flashing.

i

No Uno link is implemented.The supplied Uno test sketch manages its own display/session data. It does not communicate with the SNTCH firmware; do not make an Uno necessary for class use.

Optional WROOM TFT/button smoke test

This separate sketch checks an ST7735 1.8-inch SPI display and four physical buttons. It does not add a display to the SNTCH classroom firmware or link the display to class sessions.

Check voltage before connecting the display.ESP32 GPIO is 3.3 V. The exact TFT breakout’s VCC and backlight circuitry are unknown; check its labels/schematic and logic compatibility. Avoid GPIO6–11 (module flash) and GPIO12 (boot strapping) for this map.

03

First-time firmware setup

Build and flash the WROOM target explicitly. Confirm board markings before uploading.

Open the firmware project

Use a terminal in this repository, then move into firmware/. Install PlatformIO Core and allow it to download the Espressif Arduino framework and toolchain on the first build.

cd firmware

Build for the WROOM-32D

The default environment is esp32wroom32d, board ID esp32dev. Build the application:

pio run -e esp32wroom32d

Initialize LittleFS only for a confirmed fresh installation

For a new device with no classroom files to preserve, make the image and write it once:

pio run -e esp32wroom32d -t buildfs
pio run -e esp32wroom32d -t uploadfs

The image carries a pending first-use marker; on boot, SNTCH writes its initial supported state and commits the installed marker.

Upload the firmware

Connect the confirmed WROOM carrier over USB, choose its serial port if prompted, then flash the application:

pio run -e esp32wroom32d -t upload

Read startup logs

Open the serial monitor at the configured 115200 baud:

pio device monitor -b 115200

Look for LittleFS mounted, classroom state loaded/initialized, access point up, HTTP API listening, and the final ready message.

!

Do not run uploadfs as routine troubleshooting.It replaces the filesystem partition and erases stored classroom files. A mount failure is ambiguous, so firmware never formats automatically. If this board has valuable data, stop at a storage error and preserve/inspect it before considering any filesystem write or full flash erase.

✓

Existing valid SNTCH state is kept.Normal application upload does not ask the firmware to format LittleFS. Valid legacy state can receive an initialization marker without changing the classroom state format.

04

Connect the Android app

Join the controller’s network even if Android reports that it has no internet.

1 · Join Wi-FiSSID SNTCH-EXAM
Password sntch-1234
2 · Check the addressOpen http://192.168.4.1/ on the connected phone.
3 · Check HTTP APIVisit /api/health and inspect the JSON response.
4 · Test in the appUse the app’s address field and Test control.

Expected health response

{
  "ok": true,
  "firmware": "0.1.0",
  "ssid": "SNTCH-EXAM",
  "ip": "192.168.4.1",
  "storageError": false
}

The real response also includes device name, uptime, connected-state counts, heap, and storage totals.

Read the checks separately

  • Seeing the Wi-Fi name means the access point is advertising.
  • Joining it means the phone associated with the controller.
  • A valid JSON response from /api/health means the phone reached the HTTP listener and health route.
  • The app’s Test result checks its own configured address and response parsing.

A health response does not prove teacher login, student join, answer submission, or results. Test those workflows too.

i

“No internet” is expected.Android may offer to switch back to mobile data. Stay connected to SNTCH-EXAM while using SNTCH; all app traffic for the classroom goes to the local controller.

Run a class

  1. Connect to SNTCH-EXAM. Open SNTCH, choose Teacher, check the controller address, and tap Test.
  2. Sign in with the teacher PIN configured in the firmware build. The current source default is 246810; change it before a real class.
  3. Open Students and add roster lines as number, name, section. Importing an existing number updates that student.
  4. Create an activity or examination, then publish it. Sessions are opened for published items.
  5. Open Sessions, create a session, choose a duration if shown, and start it. Share the session code with students.
  6. Use session details to see participants and submissions; pause, resume, or end the session there.
  7. Use Attendance to select a section/date and mark present, late, or absent. The phone supplies the date.
  8. Use Results to open submissions, review activity responses, and view examination scores. Student answer review follows the configured results policy.
i

Authentication is local.The teacher PIN is a firmware build setting. Teacher tokens live in controller memory and expire; after a controller restart, sign in again.

06

Student workflow

Join the active session, complete open work, and submit once.

ConnectJoin the controller Wi-Fi; remain connected without internet.
JoinChoose Student, check the session code, enter the student number.
ParticipateOpen available activity or examination from Home.
SubmitSend the response; check submission/result status.

Activities

Write a response in the activity screen and submit it. The app keeps an edited draft locally until it is sent; the documented accepted response length is 10–500 characters.

Examinations

Start an examination when the session is live. Answers autosave as they change. Review answers before submitting; a timeout or session end may auto-submit the attempt.

Results

Completed examination results show score and pass/fail. Answer review appears when the teacher’s results policy allows it. Rejoin the same open session if prompted after reconnecting.

The app polls state while relevant screens are active. If the controller is unreachable, it keeps the last snapshot and shows a reconnect message; new server changes wait until connection returns.

07

Storage, restart and recovery

The controller protects the filesystem by stopping when it cannot trust saved class state.

→
SNTCH corevalidates and updates state
→
LittleFSstate.json, /sub, /att

What survives

Supported classroom state, roster, sessions, attendance, activities/exams, submissions, and saved exam work are stored locally. On restart, a live session is restored as paused. Authentication tokens are RAM-only, so teacher sign-in and student rejoin may be needed.

How startup decides

A pending marker in an explicitly uploaded fresh filesystem allows first state creation. An installed marker with a missing state is treated as data loss and blocks startup. Valid old SNTCH state without a marker can be adopted in place. A malformed or unsupported state is preserved and rejected.

!

Storage error? Stop before writing a filesystem image.Do not use uploadfs, formatting, or chip erase to “try a fix.” These can replace saved class files. Record serial logs, keep power stable, and back up or inspect the device using a data-preserving method before recovery.

Use checks that preserve stored data first.

09

What is verified

Software checks and physical classroom checks are different kinds of evidence.

Firmware buildPlatformIO WROOM-32D target builds for esp32dev; a successful build does not verify a board.
Portable + HTTP testsNative core tests and host HTTP/restart integration tests exercise the shared logic over simulated storage/network transport.
Android JVM testsApp data/API behavior is tested against a loopback HTTP server; this is not Android-to-ESP32 hardware testing.
Physical verificationNo claim is made here that the board was flashed, the TFT wired, or a full phone-to-controller class workflow completed.
i

Before a real class: confirm the carrier/module marking, upload the WROOM target, inspect serial logs, connect two Android devices, test health, teacher sign-in, student join, submission/results, and restart recovery.
